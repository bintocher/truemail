# Постоянно видимое состояние синхронизации почты

- Состояние: утверждена
- Утвердил: владелец проекта (утверждение выдано заранее 2026-09-16)
- Задача: issue #69
- Зависит от: error-kinds-and-messages.md
- Обновлено: 2026-09-16
- Ревизия: 2

## Цель и результат для пользователя

Сейчас состояние синхронизации почты аккаунта живёт только в памяти процесса и почти нигде не показывается: события `truemail-sync-state` из цикла `sync_accounts` и из наблюдателя за новыми письмами обрабатывает только всплывающее сообщение об ошибке, а строка состояния календаря (`#calSyncInfo`) откликается лишь на область событий `"auxiliary"` и не существующую в ядре `"dav"`. Если синхронизация аккаунта уже давно не удаётся (например, сервер отклоняет пароль после его смены на стороне провайдера), пользователь узнаёт об этом только по устаревшим письмам и никак не может отличить "ещё не досинхронизировалось" от "не может синхронизироваться вовсе". После перезапуска программы даже этот минимум пропадает - никакой истории состояния до перезапуска нет.

После изменения состояние синхронизации каждого аккаунта видно постоянно: в боковой панели рядом с аккаунтом и подробно в его карточке настроек, - и переживает перезапуск программы, потому что хранится в базе данных. Отдельно выделяется случай, когда синхронизация не может продолжиться из-за отказа входа: пользователь видит это как явное "нужен повторный вход" с прямым переходом к переподключению, а не как молчание.

## Границы задачи

- `apps/desktop/src-tauri/src/commands.rs`: цикл `sync_accounts` (3228-3352), наблюдатель за новыми письмами внутри `start_realtime` для всех провайдеров кроме Gmail (переход в `syncing` - 3474, в `ready` - 3553, в `retrying` - 3574), первичная синхронизация после подключения (`spawn_initial_mail_sync`, 4086-4137).
- `crates/core/migrations/`: новая миграция для таблицы `accounts`.
- `crates/core/src/model/account.rs` (`struct Account`) и `crates/core/src/storage/repo.rs` - новые поля и метод их обновления.
- `apps/desktop/ui/modules/mail.js:791-800` (`.acc-h` - заголовок аккаунта в боковой панели) и `apps/desktop/ui/modules/settings.js:69-90` (`renderAccountSettings`, `.account-stats`, кнопка `.account-reconnect`) - место отображения состояния.
- `apps/desktop/ui/styles.css` - стиль индикатора состояния рядом с `.acc-h`.
- Вид ошибки, безопасный текст и таблица понятных сообщений берутся из error-kinds-and-messages.md: этот документ определяет, какие виды ставят признак "нужен повторный вход" (S-016 там), а здесь описано только, как из этого признака и из вида ошибки строится постоянное состояние аккаунта и что видно в боковой панели и в карточке.

## Что не входит в задачу

- Состояние синхронизации календарей, задач и контактов (область событий `"auxiliary"`) - у него уже есть своя строка `#calSyncInfo`, отдельная от этой задачи.
- Исправление обработки несуществующей области событий `"dav"` в `apps/desktop/ui/modules/composer.js:45` - это отдельная неточность в текущем коде, выходящая за рамки хранения и показа состояния почты.
- Прогресс внутри одного прохода синхронизации (сколько папок из скольких уже прочитано) - вводится только состояние на уровне аккаунта: идёт синхронизация, повторная попытка, последняя попытка успешна, последняя попытка завершилась ошибкой, требуется повторный вход.
- Изменение самой логики выбора вида ошибки - классификация "это отказ входа" и таблица понятных сообщений полностью определены в error-kinds-and-messages.md; эта задача только использует их результат для признака "нужен повторный вход" и для текста в карточке.
- Автоматическое действие при обнаружении "нужен повторный вход" (например, всплывающее окно OAuth без участия пользователя) - только видимый признак и переход к экрану переподключения по явному действию пользователя.

## Текущее поведение и доказательства

- Цикл `sync_accounts` (`commands.rs:3228-3352`) для каждого включённого аккаунта берёт `state.syncing` (`Arc<tokio::sync::Mutex<HashSet<i64>>>`, объявлено `commands.rs:37`), вставляет `account.id` и пропускает аккаунт, если он уже синхронизируется (`if !syncing.insert(...) { continue; }`), затем публикует событие `truemail-sync-state` с областью событий `"all"` и статусом `"syncing"`, а по завершении - `"ready"` или `"error"` (`commands.rs:3313-3347`).
- Наблюдатель за новыми письмами внутри `start_realtime` запускается для всех провайдеров, кроме Gmail (`if account.provider != Provider::Gmail`, `commands.rs:3454`) - у Gmail вместо него отдельный лёгкий REST polling (комментарий в коде, `commands.rs:3452-3453`), и его исход попадает в постоянное состояние только через цикл `sync_accounts`, а не через отдельную область событий; отдельного цикла со своими событиями у Gmail нет. Наблюдатель использует тот же самый мьютекс - `let watch_syncing = state.syncing.clone()` (`commands.rs:3456`) - и перед каждым проходом ждёт в цикле `loop { if syncing.insert(...) break; sleep(250ms) }` (`commands.rs:3480-3483`), пока область событий `"all"` не освободит аккаунт. Это значит, что для одного аккаунта проходы из `sync_accounts` и из наблюдателя уже физически не выполняются одновременно - они лишь чередуются во времени, каждый следующий проход просто перезаписывает предыдущий результат.
- Первичная синхронизация после подключения (`spawn_initial_mail_sync`, `commands.rs:4086-4137`) не публикует `truemail-sync-state` вовсе - только `truemail-data-changed` и запись в журнал; между статусом "подключено" и первым исходом синхронизации почты в интерфейсе сейчас нет никакого признака.
- В цикле `sync_accounts` при частичном исходе - почта не синхронизировалась, а календарь и контакты синхронизировались успешно (`(Err(mail_error), Ok(aux)) if supports_auxiliary`, `commands.rs:3310-3323`) - событие всё равно публикуется со статусом `"ready"` и текстом ошибки почты внутри `warnings`, а не со статусом `"error"`.
- Результат прохода нигде не сохраняется, кроме передачи в событие `truemail-sync-state`, которое слушает только `apps/desktop/ui/bridge.js:257` (`tauri.event.listen(...)`) и обрабатывает `window.handleSyncState` (`composer.js:45`). Эта функция реагирует на статус `"error"` показом всплывающего сообщения и на область событий `"dav"`/`"auxiliary"` - обновлением `#calSyncInfo`; для `"all"` и `"mail"` строка `#calSyncInfo` не обновляется вовсе, а `"syncing"`/`"ready"` без ошибки не показывает ничего.
- В таблице `accounts` (`crates/core/migrations/0001_accounts.sql:4-30`) нет ни одного поля про историю или текущее состояние синхронизации почты - только конфигурация подключения. Единственное поле с похожим назначением, `last_synced`, относится к таблице `folders` (`crates/core/src/storage/repo.rs:671,736,871`) и обновляется как часть чтения конкретной папки, а не как признак состояния всего аккаунта.
- Заголовок аккаунта в боковой панели (`.acc-h`, `mail.js:791-800`) строится из аватара, адреса и шеврона раскрытия (`header.innerHTML=... <span class="ava">...<span class="em">...<span class="chev">...`); признака состояния синхронизации в разметке нет.
- Карточка аккаунта в настройках (`renderAccountSettings`, `settings.js:69`) показывает `.account-stats` как статичный текст "N папок · M календарей" и кнопку `.account-reconnect`, которая уже открывает экран переподключения через `showAccountWizard(account.email)` (`settings.js`, обработчик `.account-reconnect`); никакого текста про успех или неуспех последней синхронизации там нет.
- После перезапуска программы состояние синхронизации, которое было видно (если было) через события в предыдущем сеансе, полностью теряется: `state.syncing` создаётся заново пустым (`main.rs:259`), и до первого нового прохода в интерфейсе нет никакого признака прошлых успехов или неудач.

## Термины и состояния

- Область событий - поле `scope` события `truemail-sync-state` со значениями `"all"` (цикл `sync_accounts`), `"mail"` (наблюдатель за новыми письмами, кроме Gmail) и `"auxiliary"`/`"dav"` (календарь, контакты, задачи - не входит в эту задачу).
- Проход синхронизации почты - вызов, который обновляет папки аккаунта и завершается успехом или ошибкой: `sync_mail_account` (`crates/core/src/account/mod.rs:2531`) в цикле `sync_accounts` и в первичной синхронизации после подключения, либо `sync_mail_inbox`/`sync_mail_inbox_delta` - более лёгкий путь наблюдателя за новыми письмами для всех провайдеров, кроме Gmail, у которого такого наблюдателя нет.
- Состояние синхронизации аккаунта - хранимая в базе данных совокупность значений: время последнего успешного прохода, безопасный текст последней ошибки (если последний проход завершился неудачей), её машиночитаемый вид и признак "нужен повторный вход".
- Нужен повторный вход - состояние, при котором вид последней ошибки синхронизации входит в список видов, требующих повторного входа (error-kinds-and-messages.md, S-016), и синхронизация не сможет продолжиться без обновления учётных данных пользователем.
- Идёт синхронизация - переходное отображаемое состояние на время выполнения прохода, отдельное от сохранённого в базе исхода прошлого прохода.
- Повторная попытка - переходное отображаемое состояние, когда наблюдатель за новыми письмами восстанавливает соединение после разрыва (статус `"retrying"`); отдельное и от сохранённого в базе исхода, и от простого "идёт синхронизация".

## Требования

### S-001. Состояние синхронизации хранится в базе данных

Система SHALL хранить для каждого аккаунта в таблице `accounts` время последнего успешного прохода синхронизации почты, безопасный текст последней ошибки синхронизации почты, её машиночитаемый вид по error-kinds-and-messages.md и признак "нужен повторный вход", сохраняющиеся между запусками программы.

### S-002. Время успеха обновляется по завершении удачного прохода

WHEN проход синхронизации почты аккаунта (цикл `sync_accounts`, наблюдатель за новыми письмами или первичная синхронизация после подключения) завершается успехом, система SHALL записать текущее время как время последней успешной синхронизации этого аккаунта и очистить сохранённые текст, вид последней ошибки и признак "нужен повторный вход".

### S-003. Текст и вид ошибки обновляются по завершении неудачного прохода

IF проход синхронизации почты аккаунта завершается ошибкой, THEN система SHALL сохранить безопасный текст и машиночитаемый вид этой ошибки как последнюю ошибку синхронизации аккаунта по фактическому результату вызова, не изменяя при этом время последней успешной синхронизации.

### S-004. Признак "нужен повторный вход" при отказе авторизации

IF вид ошибки, которой завершился проход синхронизации почты аккаунта, входит в список видов, требующих повторного входа (error-kinds-and-messages.md, S-016), THEN система SHALL установить для этого аккаунта признак "нужен повторный вход".

### S-005. Снятие признака "нужен повторный вход" при успехе

WHEN проход синхронизации почты аккаунта завершается успехом, система SHALL снять для этого аккаунта признак "нужен повторный вход", если он был установлен ранее.

### S-006. Признак состояния виден в боковой панели постоянно

WHILE аккаунт присутствует в списке аккаунтов боковой панели, система SHALL показывать рядом с его заголовком один из признаков - идёт синхронизация, повторная попытка, последний проход завершился ошибкой, требуется повторный вход, - либо не показывать признак, когда последний сохранённый проход был успешен и активного прохода сейчас нет.

### S-007. Полный приоритет отображаемых состояний

IF для аккаунта одновременно верны несколько отображаемых состояний, THEN система SHALL показать ровно одно по убыванию приоритета: "нужен повторный вход" выше сохранённой ошибки, сохранённая ошибка выше "повторной попытки", "повторная попытка" выше "идёт синхронизация", а "идёт синхронизация" выше отсутствия индикатора при последнем успешном проходе.

### S-008. Состояние переживает перезапуск программы

WHEN программа запускается заново, система SHALL показать в боковой панели и в карточке аккаунта состояние синхронизации, сохранённое в базе данных до перезапуска, до того, как выполнится хотя бы один новый проход синхронизации в этом сеансе.

### S-009. Подробности состояния в карточке аккаунта

WHEN пользователь открывает карточку аккаунта в настройках, система SHALL показать время последней успешной синхронизации почты этого аккаунта, а если последний проход завершился ошибкой - локализованный текст по её виду из error-kinds-and-messages.md с исходным безопасным текстом только в раскрываемых подробностях, либо, если для аккаунта установлен признак "нужен повторный вход", сообщение о необходимости повторного входа с действием переподключения вместо текста обычной ошибки.

### S-010. Переход к переподключению из признака "нужен повторный вход"

WHEN аккаунт находится в состоянии "нужен повторный вход" и пользователь нажимает на признак этого состояния в боковой панели или в карточке настроек, система SHALL открыть экран переподключения аккаунта тем же способом, что и существующая кнопка "Переподключить".

### S-011. Отображение переходных состояний не стирает сохранённую ошибку

WHILE проход синхронизации почты аккаунта выполняется, система SHALL показывать признак "идёт синхронизация" или "повторная попытка" по текущему событию, не удаляя из базы данных и не пряча сохранённый признак "нужен повторный вход" или текст последней ошибки до тех пор, пока проход не завершится новым исходом по S-002 или S-003.

### S-012. Первая синхронизация тоже сообщает о начале и об исходе

WHEN запускается первая синхронизация почты сразу после подключения аккаунта (`spawn_initial_mail_sync`), система SHALL опубликовать событие `truemail-sync-state` со статусом `syncing` в начале и со статусом `ready` или `error` по завершении, так же как это делает цикл `sync_accounts`.

### S-013. Частичный исход цикла не скрывает неуспех почты

IF в рамках одного прохода цикла `sync_accounts` почта аккаунта не синхронизировалась, а вспомогательные данные (календарь, контакты, задачи) синхронизировались успешно, THEN система SHALL записать в базу данных неуспех именно почтовой синхронизации по S-003 и S-004, даже когда опубликованное для этого прохода событие `truemail-sync-state` сообщает статус `ready` с предупреждениями.

## Интерфейсы и данные

- Новая миграция `crates/core/migrations/0039_account_sync_state.sql` добавляет в таблицу `accounts` четыре столбца: `last_sync_at TEXT NULL` (время последнего успешного прохода, формат как у существующих `created_at`/`updated_at`), `last_sync_error TEXT NULL` (безопасный текст последней ошибки), `last_sync_error_kind TEXT NULL` (её машиночитаемый вид по error-kinds-and-messages.md), `needs_reauth INTEGER NOT NULL DEFAULT 0` (0/1).
- `struct Account` (`crates/core/src/model/account.rs:49-74`) получает четыре новых публичных поля: `last_sync_at: Option<String>`, `last_sync_error: Option<String>`, `last_sync_error_kind: Option<String>`, `needs_reauth: bool` - они уже попадают в JSON-ответ `list_accounts` и в объект `account` в `ConnectedAccount`, без введения отдельной команды Tauri.
- Новый метод хранилища, например `Db::record_mail_sync_outcome(account_id, outcome)`, где `outcome` - успех (обновляет `last_sync_at`, очищает `last_sync_error`, `last_sync_error_kind` и `needs_reauth`) либо ошибка с текстом, видом и признаком отказа авторизации (обновляет `last_sync_error`, `last_sync_error_kind` и `needs_reauth`, не трогая `last_sync_at`). Вызывается по фактическому результату (`Ok`/`Err`) вызова прохода из трёх мест: `sync_accounts`, наблюдателя за новыми письмами в `start_realtime`, `spawn_initial_mail_sync` - а не по тексту опубликованного события `truemail-sync-state`, потому что они могут расходиться, как в частичном исходе цикла (S-013).
- Событие `truemail-sync-state` сохраняет прежние поля и расширяется двумя необязательными - `error_kind` и `error_message` - по общей форме из error-kinds-and-messages.md (S-004 там); оно по-прежнему сигнализирует о переходных статусах `"syncing"`/`"ready"`/`"error"`/`"retrying"` (S-011), а постоянное состояние читается из полей аккаунта, приходящих через `list_accounts` и `truemail-data-changed`.
- В боковой панели (`.acc-h`, `mail.js`) и в карточке аккаунта (`.account-stats`, `settings.js`) добавляется элемент индикатора состояния; новый CSS-класс по образцу уже существующего `.spinner` (`styles.css:178`) для признаков "идёт синхронизация" и "повторная попытка".

## Ошибки и частичные отказы

- Безопасный текст ошибки в `last_sync_error` и её вид в `last_sync_error_kind` формируются по общим правилам error-kinds-and-messages.md (включая очистку секретов, S-010 там); в карточке аккаунта по умолчанию показывается локализованный текст по виду, а исходный текст - только в раскрываемых подробностях (S-009).
- Если проход синхронизации не начался вовсе (аккаунт отключён, `enabled = false`), состояние синхронизации не обновляется и остаётся таким, каким было до отключения аккаунта.
- Ошибка записи нового состояния в базу данных (например, база временно заблокирована) не должна прерывать сам проход синхронизации: письма, уже сохранённые в этом проходе, остаются сохранёнными. Очереди повторов для такой записи нет: неудачная запись состояния теряется без следа, а видимое состояние отражает исход только следующего успешно записанного прохода.

## Одновременная работа, повторы и защита от дублей

- Для одного аккаунта проходы синхронизации почты из цикла `sync_accounts` и из наблюдателя за новыми письмами уже физически не выполняются одновременно - оба используют общий `state.syncing` (`commands.rs:37,3456`), поэтому отдельной защиты от параллельной записи состояния одного и того же аккаунта не требуется: на запись состояния всегда приходит ровно один завершившийся проход.
- Первичная синхронизация после подключения (`spawn_initial_mail_sync`) точно так же проверяет и занимает `state.syncing` (`commands.rs:4092-4096`) перед тем, как начать проход, поэтому не может пересекаться по времени с циклом `sync_accounts` или наблюдателем для того же аккаунта.

## Безопасность и конфиденциальность

- `last_sync_error` и `last_sync_error_kind` хранятся в зашифрованной локальной базе (SQLCipher) наравне с прочими данными аккаунта и не покидают устройство; отдельного маскирования в базе не требуется - это тот же уровень защиты, что и у остальных данных аккаунта.
- Признак "нужен повторный вход" не раскрывает пароль или причину отказа за пределами текста ошибки, который и так уже виден администратору при разборе через журнал.

## Совместимость, перенос данных и откат

- Новые столбцы добавляются миграцией со значениями по умолчанию (`NULL`/`0`), поэтому у существующих аккаунтов состояние синхронизации после обновления просто отсутствует до первого прохода - это не мешает загрузке и работе программы.
- Откат - это возврат кода предыдущей версии, который эти столбцы не читает и не пишет; сами столбцы при откате остаются в таблице `accounts` без использования, удалять их не требуется, а данные писем и настроек откат не затрагивает.

## Скорость и потребление ресурсов

- Запись состояния - одно обновление четырёх столбцов одной строки `accounts` по завершении прохода, не чаще, чем сейчас происходят сами проходы синхронизации; ощутимой дополнительной нагрузки на базу данных это не добавляет.
- Чтение состояния идёт вместе с уже существующим `list_accounts`, поэтому дополнительных сетевых или файловых обращений для отображения признака в боковой панели не требуется.

## Журналы, метрики и эксплуатация

- Изменение признака "нужен повторный вход" для аккаунта дополнительно попадает в уже существующие журнальные записи об ошибке синхронизации (`tracing::error!`/`tracing::warn!` в `commands.rs`), не требуя нового отдельного журнала.

## Отклонённые варианты

- Держать состояние синхронизации только в памяти, но переживать перезапуск через повторный проход сразу при старте программы. Отклонено: это не то же самое, что видимое сохранённое состояние - пользователь увидит не последнее известное состояние, а "идёт синхронизация" сразу после запуска, и на время первого прохода информация об истории всё равно потеряна.
- Отдельная таблица истории проходов синхронизации вместо четырёх столбцов в `accounts`. Отклонено как избыточное для задачи: нужен только последний исход, а не история всех проходов; полноценный журнал проходов - самостоятельная более крупная задача.
- Показ признака состояния только в карточке настроек, без боковой панели. Отклонено: рамки задачи прямо требуют состояние, видимое постоянно, а карточка настроек открыта не всегда - боковая панель видна во время обычной работы с почтой.
- Очередь повторов для неудачной записи состояния в базу. Отклонено как отдельная задача: очереди повторов в проекте сейчас нет ни для одной похожей записи, а честная потеря одной записи состояния безопаснее, чем неявная очередь без контроля переполнения.
